# 멀티캠 타임코드 좌표계 버그 (2026-08-19)

엔진 `feat/issue-8-9-container` / 앱 v0.13.43.

사용자 제보(테스터, 릴리스 v0.13.4): 멀티캠 11개짜리 프로젝트가 통째로 거부됐다.

> 메인 스토리라인이 멀티캠 클립으로만 구성되어 오디오를 분석할 수 없습니다 —
> 타임라인에서 클립을 전체 선택해 '클립 항목 분해(Break Apart Clip Items)' 후
> 다시 내보내 주세요

**이 메시지는 원인이 아니다.** 로그가 진짜 사유를 갖고 있었고, 11개 전부 같았다:

```
[scan] 멀티캠 'Untitled Multicam Clip' 내부 'Gap' 배치가 겹치거나
       역순(offset 0.000 < 앞 항목 끝 17993.976) — 분석 없이 통째 보존
[scan] 스파인 직속 11개(오디오 0) — 분석 대상(오디오) 0 / 통과 11
```

17993.976s(≈4h59m54s)는 그 멀티캠의 `tcStart` — 카메라 타임코드다.

---

## 1. 원인 — 좌표계가 두 갈래인데 하나로 봤다

실측(`~/Movies/김사랑 집사 멀티캠 완료.fcpxmld`):

| 대상 | 값 | 좌표계 |
|---|---|---|
| `<multicam tcStart>` | 3603.6s | 타임코드 |
| `<mc-clip start>` | 5320.398s | **타임코드** |
| `<mc-angle>` 첫 자식 `<gap offset>` | **0s** | **앵글 로컬** |
| 그 다음 자식 offset | 2.4608s (= 앞 갭 길이) | 앵글 로컬 |

컴파운드 `<sequence><spine>`은 자식 offset이 시퀀스 `tcStart` 공간이라 기존 가정이
맞았다. 멀티캠 `<mc-angle>`만 0에서 시작한다. 그런데 `_compound_spine_items`가
커서를 `tcStart`에서 출발시키므로 **첫 자식부터** `offset 0 < tcStart`로 걸린다.

### 첫 수정은 틀렸다 — 관례가 둘이다

처음엔 "mc-angle 자식은 항상 0 기준"으로 못 박았다. 그러자 기존 픽스처
`mc_trimmed`의 평면 등가 검증이 깨졌다(자막 5 ≠ 평면 8). 그 픽스처는 앵글 자식
offset이 `tcStart` 공간(3600s, tcStart=3600s)이다. **두 관례가 실제로 공존한다.**

최종 규칙 — **항목이 리소스 원점보다 앞설 수는 없다**: 첫 lane-0 자식의 offset이
`tcStart`보다 작으면 그 앵글은 0 기준이므로 `tcStart`를 더한다. `tcStart=0`이면
두 해석이 같아 무영향. 모든 호출자가 지나가는 `_compound_spine_items` 한 곳에서 끝난다.

## 2. 왜 여태 안 잡혔나 — 픽스처가 전부 `tcStart="0s"`

`tcStart`가 0이면 더할 값이 0이라 **실수가 무해하다.** 기존 멀티캠 픽스처
(`mc_audio_angle`, `mc_angle_switch`, `mc_trimmed`, …)가 전부 `tcStart="0s"`였다.

로컬 샘플에서도 그대로 갈렸다:

| 파일 | multicam tcStart | 수정 전 → 후 (오디오 항목) |
|---|---:|---|
| Introducing Allie Sherlock | 0.0 | 22 → 22 (우연히 정상) |
| 2025 나눔봉사단 홍보영상 | 19414.9 | **107 → 115** |
| 2025 나눔봉사단 홍보영상2 | 19414.9 | **106 → 114** |
| 김사랑 집사 멀티캠 완료 | 3603.6 | **0 → 9** |
| 제보 프로젝트 | 17993.976 | 0 → (전량 거부) |

카메라 타임코드로 싱크한 멀티캠 — 즉 **실무에서 흔한 쪽**이 전부 해당한다.
`tcStart=0`이 아닌 픽스처 `mc_camera_timecode`를 추가했다.

## 3. 오류보다 나쁜 경우가 있었다

거부는 예외가 아니라 `분석 없이 통째 보존`이다. 스파인에 다른 오디오가 하나라도
있으면 **성공한 것처럼 끝나고 자막에만 구멍이 난다.** 나눔봉사단 두 파일에서
각각 8구간이 그렇게 조용히 빠지고 있었다. 스파인이 전부 멀티캠일 때만 오류로
드러난다 — 제보자가 그 경우였다.

## 4. 매핑 검증 (개수만 맞으면 안 된다)

시각이 틀리면 오류 없이 자막이 어긋나므로 손계산과 대조했다.

**픽스처** — mc-clip `start=3620`, multicam `tcStart=3600`:
```
3620 − 3600 = 앵글 로컬 20s
앵글: gap[0~5) → 마이크 클립(offset 5, start 3600)
20 − 5 = 클립 안 15s  →  소스 TC 3600+15 = 3615
3615 − asset.start 3600 = 파일 안 15.0s     ← 엔진 출력 15.0 ✓
```

**실파일** — mc-clip `start=5320.398`, `tcStart=3603.6`, asset `start=3603.6`:
```
5320.398 − 3603.6 = 1716.798                ← 엔진 출력 1716.798 ✓
길이 9.135 ≈ mc-clip duration 9.134 ✓
```

멀티캠 포함 프로젝트 전체 실행도 통과(48항목 / 오디오 22 / 자막 21개 / 14.3초).

## 5. 오류 메시지에 사유를 붙였다

사유 없이 "멀티캠으로만 구성"이라고만 하면 **"이 앱은 멀티캠을 지원하지 않는구나"**
로 읽힌다 — 제보자가 실제로 그렇게 읽었다. `timeline_scan.skip_reasons()`가 직전
스캔의 거부 사유를 남기고, 엔진이 오류 뒤에 붙인다:

```
오류: 메인 스토리라인이 멀티캠 클립으로만 구성되어 … 다시 내보내 주세요
사유: 멀티캠: 리타임(timeMap)
```

## 6. 회귀를 놓칠 뻔했다 — pytest가 그 스위트를 안 돌린다

`silence_cutter/tests/test_multicam.py`는 `__main__`에서 `run_all()`을 부르는 자체
러너라 **pytest가 수집하지 않는다.** 그래서 `pytest -q`가 "219 passed"를 찍는 동안
`mc_trimmed`가 깨진 채 지나갔고, 나는 "회귀 없음"이라고 보고했다. 사용자가
"멀티캠 지원 안 하나?"라고 묻지 않았으면 그대로 넘어갔을 것이다.

`tests/test_multicam_suite_runs.py`로 pytest에 연결했고, 일부러 깨뜨려 실제로
실패를 잡는 것까지 확인했다. **통과 숫자를 근거로 쓰려면 그 숫자가 실제로 무엇을
돌렸는지부터 확인해야 한다.**
